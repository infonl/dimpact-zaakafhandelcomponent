## Why

ZAC's upload allowlist is enforced on the file *name* only. `AllowedFileType.isAllowed(filename)` looks at the extension and nothing else, so renaming `payload.exe` to `payload.pdf` is enough to store an executable in Open Zaak through the "add document to case or task" flow. Neither ZAC nor Open Zaak inspects the bytes. The media type the browser reports (`formaat` for documents, `type` for task uploads) is not validated either — it is deliberately ignored, because its value comes from the client operating system and varies per workstation — but it *is* forwarded unchanged and stored on the document in Open Zaak, so the media type Open Zaak holds is a client-supplied value.

The ZAC architecture board decided this should be closed as an additional security measure. The spike behind this change (PZ-1637) established, by measurement, that Apache Tika can satisfy it and that the alternative suggested in the ticket cannot: `Files.probeContentType` reports `application/pdf` for both an executable and a Word document renamed to `.pdf`, on macOS and on Linux alike, because it resolves the extension and never reads the content. `URLConnection.guessContentTypeFromStream` returns no answer at all for these files.

## What Changes

- Determine the media type of every uploaded file **from its content** using Apache Tika, and reject the upload with a 4xx when that media type does not match the file's extension. This closes both cases from the acceptance criteria: a file whose real type is not on the allowlist (an `.exe` renamed to `.pdf`), and a file whose real type is on the allowlist but does not match its extension (a `.doc` renamed to `.pdf`).
- Detect from the bytes only. Tika must **not** be given the file name: with the name as a hint it upgrades its own answer using exactly the value the attacker controls. Measured in the spike — a plain ZIP named `upload.docx` is reported as a Word document when the name is passed, and as `application/zip` when it is not.
- Extend `AllowedFileType` so each entry carries the set of media types Tika may legitimately report for that extension's content. For almost every entry that is just the existing canonical media type; two entries need an addition, because these formats are not distinguishable by content (see design.md): `.mp4` also accepts `video/quicktime`, and `.mkv` also accepts `application/x-matroska`.
- Accept a detected media type that is a Tika *specialization* of the expected one, not only an exact match. This keeps text files that happen to contain markup working: a `.txt` holding HTML or XML is detected as `text/html` / `application/xml`, both of which Tika registers as children of `text/plain`. All spoofing attempts are still rejected under this rule, because none of them is a specialization of the claimed type.
- Give the user a distinct error message for "the content does not match the extension", separate from the existing "this file type is not allowed". The frontend already renders backend validation messages, so no frontend plumbing is needed beyond the new message key.
- Stop forwarding the client-reported media type to Open Zaak. Once the server has determined the media type itself, ZAC writes the detected value into the document it sends to Open Zaak instead of the browser-supplied `formaat` / `type`. This also removes the whole class of problems where the same file type is reported differently per workstation.
- Add Apache Tika as a runtime dependency, trimmed to the artifacts detection actually needs: `tika-core`, `tika-parser-zip-commons` and `tika-parser-microsoft-module`, with the heavy parsing-only transitive dependencies excluded. Measured at 22 jars / 13.5 MB resolved, of which ZAC already ships 6, so roughly 10.5 MB and 16 jars are new.
- Explicitly out of scope: documents that do not enter through ZAC. A productaanvraag from Open Formulieren, or a document written straight to Open Zaak by SmartDocuments, is the responsibility of that component; ZAC trusts what is already stored in PodiumD. Also out of scope: virus scanning (ClamAV or otherwise) — content type detection says what a file *is*, not whether it is safe. And out of scope: the browser-side extension filter, which stays a convenience filter and is not a security boundary.

## Capabilities

### New Capabilities
- `document-upload-file-type-validation`: defines what ZAC accepts when a user uploads a file as a document on a case, as a new version of a document, or into a task form — the extension must be on the allowlist, and the file's actual content must match that extension.

## Impact

- **Affected code**: `nl.info.zac.configuration.AllowedFileType` (per-extension accepted media types, and a content-aware `isAllowed`), a new media type detector class in the same package, `ValidRestEnkelvoudigInformatieFileUploadFormValidator` and `ValidRestFileUploadFormValidator` (both already receive the full bytes), and `RestInformatieobjectConverter` (write the detected media type instead of the client-supplied one).
- **Endpoints**: no signature changes. All three multipart upload endpoints — `EnkelvoudigInformatieObjectRestService.createEnkelvoudigInformatieobjectAndUploadFile`, `EnkelvoudigInformatieObjectRestService.updateEnkelvoudigInformatieobjectAndUploadFile` and `TaskRestService.uploadFile` — already pass their form through `@Valid`, so they inherit the stricter check without modification.
- **Build**: three new `implementation` entries in `build.gradle.kts` plus a Tika version in `gradle/libs.versions.toml`. Adds `log4j-api` (via POI) to the runtime classpath, which needs a binding or bridge to avoid a logging error on startup, and enlarges the surface watched by the OWASP dependency check (POI, XMLBeans).
- **Frontend**: one new message key in `nl.json` and `en.json`. No component changes — every mutation already reports its own failures through `FoutAfhandelingService`.
- **External systems**: no contract change. Open Zaak receives the same document creation calls, with a server-determined `formaat` instead of a client-supplied one.
- **Tests**: unit tests for the detector and the extended allowlist, integration tests covering a rejected spoof and an accepted genuine file per format family, and a documented set of sample files to test against.
- **Performance**: negligible. Detection does not read the whole file — measured at 3 ms for a 78 MB Word document, under 1 ms for an 80 MB video, against ZAC's 80 MB upload limit.
