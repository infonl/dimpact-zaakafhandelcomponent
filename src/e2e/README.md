# End-to-end tests

This directory contains the end-to-end tests of ZAC. They use [Playwright](https://playwright.dev/) with
[playwright-bdd](https://vitalets.github.io/playwright-bdd), which runs Gherkin feature files with the Playwright
test runner.

Each feature file in [bdd](./bdd) is a journey: one goal of a user, followed from start to finish through the real UI.
A journey proves that the parts of ZAC work together. It does not prove each business rule; the integration tests,
the Angular specs and the OPA policy tests do that.

The cucumber-js suite in [features](./features) is being replaced, feature by feature. See
[The cucumber-js suite](#the-cucumber-js-suite).

## Running the tests

[docs/development/testing.md](../../docs/development/testing.md#end-to-end-e2e-tests) describes how to start the
local kind stack and how to run the tests against it. In this directory you can also use these commands:

| Command             | What it does                                                    |
|---------------------|-----------------------------------------------------------------|
| `npm test`          | Generates the tests from the feature files and runs them.       |
| `npm run test:ui`   | The same, in the Playwright UI.                                 |
| `npm run typecheck` | Generates the types of the REST API of ZAC and checks the types of the suite. |
| `npm run lint`      | Runs ESLint on the suite.                                       |
| `npm run test:unit` | Runs the unit tests of the suite itself, such as of its configuration. They need no stack. |

`npm test` runs `bddgen` first. Run `npx bddgen` yourself before you start one test from your IDE, also after you
change the fixtures that a step uses.

The steps call the REST API of ZAC with [openapi-fetch](https://openapi-ts.dev/openapi-fetch/), typed by the OpenAPI
spec of ZAC, like the Angular app does. The types are generated into the `generated` folder, which Git ignores.
`npm run typecheck` generates them from the spec, which the Gradle build writes. Create or update the spec first,
also after a change in the REST API of ZAC, from the root of the repository:

```shell
./gradlew generateOpenApiSpec
```

The tests themselves run without the generated types.

## Layout

| Path                                         | What it holds                                                                              |
|----------------------------------------------|--------------------------------------------------------------------------------------------|
| [playwright.config.ts](./playwright.config.ts) | The projects `setup` and `journeys`, and the settings that differ between a developer machine and CI. |
| [config/env.ts](./config/env.ts)             | `ENV`: the validated configuration of the run.                                             |
| [config/targets](./config/targets)           | One profile for each place where ZAC can run.                                              |
| [setup](./setup)                             | The setup project, which signs in once for each role.                                      |
| [bdd/fixtures.ts](./bdd/fixtures.ts)         | Exports `Given`, `When` and `Then` with the fixtures of `_core`.                           |
| [bdd/_core](./bdd/_core)                     | The fixtures that every journey can use, the sessions of the roles and the special tags.   |
| `bdd/@<domain>`                              | The feature files and the steps of one domain.                                             |
| [bdd/screens](./bdd/screens)                 | The screens of ZAC and Keycloak that more than one journey uses, such as the zaak page.    |
| [bdd/support](./bdd/support)                 | Everything behind `testData`: the ZAC REST API, the zaakafhandelparameters and the lock.   |
| `generated`                                  | The types of the ZAC REST API, generated by `npm run typecheck`. Git ignores this folder.  |

A directory name that starts with `@` is a tag of the scenarios in it. For example,
`npm test -- --grep @cmmn` runs the journeys in `bdd/@zaak/@cmmn`.

## Configuration

The target is the place where ZAC runs. `E2E_TARGET` selects a profile in [config/targets](./config/targets); the
default is `kind`. A profile holds what is not secret about a target, and reads its secrets from environment
variables. [config/targets/target.ts](./config/targets/target.ts) describes its settings:

- the URL of ZAC, or why the profile cannot tell it;
- the account of each role. A profile leaves out a role whose secrets are not set, and the scenarios of that role are
  skipped;
- the texts of the Keycloak login page, which depend on the theme and the language of the target;
- what the test doubles of the target answer, such as the BAG test double. A target without test doubles skips the
  steps that need them;
- whether the scenarios tagged `@live-env-only` run.

Everything that differs between targets belongs in the profile, so a new target needs no change in a step.

| Variable            | Meaning                                                                           | Default |
|---------------------|-----------------------------------------------------------------------------------|---------|
| `E2E_TARGET`        | The profile to use.                                                               | `kind`  |
| `KIND_CLUSTER_NAME` | Target `kind`: the kind cluster. The profile reads the port of ZAC from its ports file. | `zac`   |
| `ZAC_URL`           | Target `kind`: the URL of ZAC when ZAC does not run in the cluster.               | none    |
| `CI`                | Set by the pipeline. It selects the number of workers, the retries, the traces and the reporters. In CI a test that passes only on its retry fails the run. | none    |

The target `kind` needs no configuration and no `.env` file. It uses the accounts of the Keycloak realm seed in
[scripts/kind/seed/keycloak](../../scripts/kind/seed/keycloak). You can set the variables in a `.env` file in this
directory; see [.env.example](./.env.example).

[config/env.ts](./config/env.ts) validates the settings when the run starts and stops the run when one is not valid.
A target that cannot tell the URL of ZAC, for example because the kind stack does not run, does not stop
`bddgen`, `playwright test --list`, the type check or the lint: the setup project fails first, with the reason.
[config/env.ts](./config/env.ts) is the only place that reads `process.env`; an ESLint rule checks this. Steps and
fixtures import `ENV`.

To run the tests against another environment, add a profile to [config/targets](./config/targets) and register it in
[config/env.ts](./config/env.ts). Let it read the URL and the passwords from environment variables. The unit tests in
[config/env.test.ts](./config/env.test.ts) show what the validation accepts.

## Roles and sessions

A role tag on a feature or a scenario selects the session of the scenario:
`@behandelaar`, `@coordinator`, `@recordmanager`, `@beheerder` or `@raadpleger`. A scenario without a role tag starts
signed out.

The setup project signs in once for each role and saves the session in `.auth/<target>`. The scenarios reuse these
sessions, so only the journey about signing in uses the Keycloak login page. When the target has no account for a role,
the scenarios of that role are skipped, and the report shows why. [bdd/_core/sessions.ts](./bdd/_core/sessions.ts)
holds all of this.

## Special tags

| Tag                     | Meaning                                                                                       |
|-------------------------|-----------------------------------------------------------------------------------------------|
| `@live-env-only`        | Needs a real external system. Runs only against a target whose profile runs live scenarios.   |
| `@blocked:<Jira key>`   | Blocked by a known issue, for example `@blocked:PZ-1234`. Skipped, with the Jira key as the reason. |
| `@fixme`                | Written, but the steps are not implemented yet. playwright-bdd skips it and does not require its steps. |

[The other special tags of playwright-bdd](https://vitalets.github.io/playwright-bdd/#/writing-features/special-tags),
such as `@slow` and `@timeout:N`, work too.

## Writing a journey

- `Given` steps set up data through `testData`. `When` steps act through the UI. `Then` steps check the UI.
- A scenario makes sure that the data that it needs is present. It does not rely on another scenario or on data that
  someone set up by hand. For example, the step that names a zaaktype sets up its zaakafhandelparameters when they
  are not what the journeys expect yet.
- Scenarios run in parallel and in any order. Give every description of data that a scenario creates the text of
  `testData.unique()`, which starts with `E2E` and ends with a code of the scenario.
- Do not wait a fixed time and do not wait for `networkidle`. Use the assertions of Playwright, which wait. To wait
  for the search index, use `testData.untilZaakIsIndexed()` and check the UI once the data is indexed. Do not reload
  a page until it shows the data.
- Put what you do on a screen that more than one journey uses in [bdd/screens](./bdd/screens), and keep a screen that
  only one journey uses in its steps.
- Find elements as a user does: by role and name first, then by label or text. See
  [testing.md](../../docs/development/testing.md#using-the-right-selectors-in-the-e2e-tests). ESLint forbids CSS
  and XPath locators and `first()`, `last()` and `nth()`. When an element has no accessible name, give it one in the
  app. The tests run against the ZAC image of `main`, so until that fix is on `main`, disable the rule on that line
  with a reason that names the fix.
- Write the Gherkin keywords in English and keep the Dutch domain nouns, such as zaak, taak and zaaktype.

Steps import `Given`, `When` and `Then` from [bdd/fixtures.ts](./bdd/fixtures.ts) and are named `*.steps.ts`.
These fixtures are available in every step:

| Fixture         | What it gives                                                                                  |
|-----------------|------------------------------------------------------------------------------------------------|
| `testData`      | The data of the scenario: it makes data exist, remembers what the scenario created and waits for the search index. See [bdd/support/test-data.ts](./bdd/support/test-data.ts). |
| `accountOfRole` | The account of a role in the target.                                                           |
| `apiAs`         | A typed client for the REST API of ZAC with the session of a role, for example `apiAs("beheerder")`. Prefer an operation of `testData`, and add one there when a second journey needs the same call. |

A new kind of data, such as a zaak that a `Given` step creates, is a new operation of `testData`, so every journey
can use it. `testData` changes shared data, such as zaakafhandelparameters, in one worker at a time. It uses a lock in
the output folder of the run, so it only keeps apart the workers of one run on one machine. It does not protect a
target that several machines or pipelines use at the same time. A lock of a worker that was killed, for example when
you stop a run in the Playwright UI, is broken by the next worker that needs it.

[bdd/fixtures.ts](./bdd/fixtures.ts) is the only file that calls `createBdd`, so every step can use every fixture,
and `bddgen` imports the generated tests from it.

## The cucumber-js suite

The cucumber-js suite consists of [features](./features), [step-definitions](./step-definitions),
[support](./support) and [utils](./utils). It runs against the TEST environment; see
[testing.md](../../docs/development/testing.md#the-cucumber-js-suite). A feature of this suite is deleted in the
pull request that adds the journeys that replace it.

Its BPMN feature uploads the [process definition](./testdata/E2ETestProcessDefinition.bpmn) and the forms in
[testdata](./testdata) to the environment that it runs against.
